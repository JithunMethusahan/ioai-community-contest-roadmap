## ⚡ Core Idea
- Choose `cuda` when available, otherwise `cpu`; move both model and every batch tensor to that device.
- `pin_memory=True` plus `.to(device, non_blocking=True)` can improve CUDA input transfer.
- CUDA is asynchronous; synchronize or use CUDA events for valid timing.
- Mixed precision uses autocast and (when needed) GradScaler to improve throughput on supported GPUs.

## ⚠️ 3 Contest Traps
1. Model on GPU but labels on CPU causes a device mismatch.
2. Repeated `.item()` calls in the training loop force synchronization and slow training.
3. Hard-coding CUDA makes a solution fail on CPU-only judges.

## 💻 Copy-Paste Contest Starter Code
```python
import torch
from torch import nn
device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model = nn.Linear(20, 4).to(device)
opt = torch.optim.AdamW(model.parameters(), lr=1e-3)
amp = device.type == "cuda"
scaler = torch.amp.GradScaler("cuda", enabled=amp)
for _ in range(5):
    x = torch.randn(64, 20, device=device)
    y = torch.randint(0, 4, (64,), device=device)
    opt.zero_grad(set_to_none=True)
    with torch.autocast(device_type=device.type, enabled=amp):
        loss = nn.functional.cross_entropy(model(x), y)
    scaler.scale(loss).backward()
    scaler.step(opt)
    scaler.update()
print(device, float(loss.detach().cpu()))
```

## ✅ Quick Check
<details><summary>Q1 — What must move to the GPU with the model?</summary>

A) Weights only B) Inputs and targets too C) Optimizer only

**Answer:** B. Tensors in an operation must be on compatible devices.
</details>

<details><summary>Q2 — Why synchronize CUDA before timing?</summary>

A) GPU work is asynchronous B) CUDA caches labels C) It changes precision

**Answer:** A. Host timing otherwise measures launch overhead, not completed work.
</details>

<details><summary>Q3 — Most portable device selection?</summary>

A) Hard-code cuda B) Always cuda:0 C) CUDA if available, else CPU

**Answer:** C. The evaluation machine may not have a GPU.
</details>
